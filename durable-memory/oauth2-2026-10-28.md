# OAuth2 for lmconn (2026-10-28)

The third wave closed the OAuth2 gap named in `docs/n8n-coverage.md`: a new
`oauth` area (`src/cmd-oauth.js`) with `authorize`, `refresh` and `status`,
and `http request --auth SERVICE` falling back to a stored OAuth access
token. This page records the decisions; the README documents the commands.

## Why we read n8n's source

n8n is the open-source reference for "connector OAuth2 that works for 400
services". Rather than design from the RFCs alone we mined its installed
package (`$(npm root -g)/n8n`) for the facts that make real providers work:

- OAuth2 credentials are data, not code: per-service `authUrl`,
  `accessTokenUrl`, `scope`, `grantType` (authorizationCode,
  clientCredentials, pkce), extra `authQueryParameters` (Google needs
  `access_type=offline&prompt=consent` to issue a refresh token) and the
  client-authentication style, `header` (HTTP Basic) or `body` (client_id
  and client_secret as form fields).
- The token response is stored whole plus a computed expiry
  (`expires_at = now + expires_in`). On use, an expired token triggers the
  refresh grant; when the provider omits a new `refresh_token` the old one
  is kept; `invalid_grant` means the user must reconnect.
- PKCE: `code_verifier = base64url(32 random bytes)`,
  `code_challenge = base64url(sha256(verifier))`, method `S256`.
- A random `state` on the redirect, verified on the callback, against CSRF.

lmconn adopts exactly these behaviours, with PKCE on by default
(`--no-pkce` opts out) because every modern provider accepts it and it
protects the loopback redirect.

## Pinned storage contract

All OAuth state lives in the existing SQLite credential table
(`src/creds.js`, `getCred`/`setCred`/`deleteCred`) as fields on the service
row, prefixed `oauth_`:

| Field | Set by | Meaning |
|---|---|---|
| `oauth_client_id`, `oauth_client_secret` | user (`cred set`) or `authorize` flags | client registration |
| `oauth_auth_url`, `oauth_token_url`, `oauth_scope`, `oauth_auth_query`, `oauth_auth_style` | same | provider configuration; flags win over the store and are written back |
| `oauth_access_token`, `oauth_token_type` | `authorize`, `refresh` | the bearer token |
| `oauth_refresh_token` | `authorize`, kept by `refresh` when the response omits one | long-lived grant |
| `oauth_expires_at` | `authorize`, `refresh` | ISO 8601 instant |

No new table, no new file: `cred list` keeps showing names only, so the
`oauth_access_token` field name may appear there while its value never does.
Envelopes report `expiresAt`, `hasRefreshToken`, `scope` and `tokenUrl`,
never a token.

## `--auth` fallback order

`lmconn http request --auth SERVICE` resolves the bearer value in this order:

1. store `api_key` for SERVICE;
2. environment variable `<SERVICE>_API_KEY`;
3. store `oauth_access_token`, refreshing first when `oauth_expires_at` has
   passed and an `oauth_refresh_token` exists, then using the fresh token.

The envelope shape is unchanged. `resolveKey` in `src/providers/index.js`
(the LLM path) is deliberately untouched: providers take API keys.

## Testing strategy: mock identity provider

The flow is tested end to end against a local `node:http` identity
provider in the test file: it serves the authorize redirect (honouring
`state` and `code_challenge`), the token endpoint (checking the PKCE
verifier, the client authentication style, `grant_type`), a refresh that
omits `refresh_token`, and an `invalid_grant` answer. Tests point
`LMCONN_DB` at a temp file and call `closeDb()` before removing it (Windows
holds open SQLite files). The loopback server binds `127.0.0.1` on an
ephemeral port (`--port 0`) so parallel test runs never collide.

Real-provider testing stays manual: a browser login cannot run in CI,
provider client registrations are per-person secrets, and the provider's
behaviour (consent screens, refresh-token issuance) depends on account
state. The `--manual` path, pasting the redirect URL on stdin, exists for
the same reason: headless machines and CI runners have no browser.

## Bun compile constraints

The release artefacts are `bun build --compile` binaries, which shaped the
code:

- Only Node built-ins that Bun implements: `node:http` for the loopback
  server, `node:crypto` for PKCE and `state`, global `fetch` for the token
  endpoint, `node:sqlite` for the store.
- No template-literal dynamic imports: the bundler cannot see
  `import(\`./cmd-${area}.js\`)`. New areas register in `AREA_LOADERS`
  in `src/schema.js` and the `AREAS` set in `src/main.js` (shared files;
  the commit message says so).
- No runtime reads of the package tree other than `package.json` through
  `import.meta.url`.
- Every new operation gets a line in `scripts/smoke.js`, which runs
  against the compiled binary on linux, macOS and Windows in CI. For this
  wave: the operation count (11 to 14), `--cli-schema` listing the three
  `oauth_*` operations, and `oauth status not-a-service` returning a clean
  envelope with nothing token-shaped on stdout.
